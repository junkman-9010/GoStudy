# 🔍 심화 기술 분석 (Technical Deep Dive): Go Program Structure & Execution

### 1. 왜 반드시 `package main`이어야 하는가?
Go 언어에서 소스 파일은 모두 특정 패키지에 속합니다. Go 컴파일러는 프로그램의 시작점을 찾기 위해 특정 규칙을 따릅니다.
- **실행 가능한 프로그램 (Executable)**: 반드시 `package main` 선언을 포함해야 합니다. 컴파일러는 이 패키지를 발견했을 때, 프로그램의 진입점(Entry Point)을 찾을 준비를 합니다.
- **라이브러리 패키지 (Library)**: `package main`이 아닌 다른 이름(예: `package math`, `package utils`)을 사용하는 패키지들은 다른 프로그램에서 불러와 사용할 수 있는 재사용 가능한 코드 묶음입니다. 이들은 단독으로 실행될 수 없으며, 반드시 다른 `package main` 프로그램에 `import`되어야 합니다.

### 2. `func main()`의 역할: 프로그램의 심장
`package main` 내에 정의된 `func main()`은 특별한 함수입니다.
- **진입점 (Entry Point)**: 운영체제가 프로그램을 실행하면, Go 런타임은 가장 먼저 `main()` 함수를 찾아 실행합니다. 
- **생명 주기**: `main()` 함수의 실행이 완료되면 프로그램의 모든 프로세스는 종료됩니다. 이 함수 내에서 호출된 다른 함수들이 아무리 복잡하더라도, `main()`이 종료되면 프로그램 전체의 실행 흐로가 마무리됩니다.

### 3. `import` 구문과 표준 라이브러리
Go의 강력한 기능 중 하나는 풍부한 표준 라이브 라이브러리입니다.
- **`import "fmt"`**: `fmt` 패키지는 'format'의 약자로, 텍스트 출력, 문자열 포매팅 등 입출력(I/O)에 필요한 핵심 기능을 제공합니다.
- **자동 관리**: `go mod tidy`를 사용하면 코드 내의 `import` 문을 분석하여, 필요한 패키지만 `go.mod`에 기록하고 사용하지 않는 패키지는 제거하여 의존성을 최적화합니다.

### 4. `go run` vs `go build`: 개발과 배포의 차이
두 명령어는 내부적으로는 컴파일 과정을 공유하지만, 사용 목적과 동작 방식에서 명확한 차이가 있습니다.

| 방식 | 명령어 | 특징 | 사용 시나리오 |
| :--- | :--- | :--- | :--- |
| **개발용 (Running)** | `go run example.go` | 컴파일 $\to$ 실행 $\to$ 임시 바이너리 삭제 | 코드 수정 후 즉각적인 결과 확인이 필요한 개발 단계. |
| **배포용 (Building)** | `go build -o app` | 컴파일 $\to$ 영구적인 바이너리 생성 | 서버 배포, 클라이언트 배포 등 실행 파일을 파일로 보관해야 하는 단계. |

- **`go run`의 내부 동작**: 컴파일러는 소스 코드를 컴파일하여 임시 디렉토리에 바이너리를 생성한 뒤, 이를 실행합니다. 실행이 끝나면 생성된 임시 파일은 자동으로 삭제되므로 시스템에 찌꺼기를 남기지 않습니다.
- **`go build`의 내부 동작**: 컴파일된 결과물을 사용자가 지정한 이름(또/은 기본 이름)으로 디스크에 파일로 저장합니다. 이 파일은 Go가 설치되지 않은 환경에서도(정적 컴파일 시) 실행할 수 있는 독립적인 실행 파일이 됩니다.
