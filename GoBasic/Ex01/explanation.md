# 🔍 심화 기술 분석 (Technical Deep Dive)

### 1. Module-Aware Go의 작동 원리
Go 1.11 버전 이후 도입된 모듈 시스템은 기존 `GOPATH` 방식의 치명적인 한계를 극복했습니다. 과거에는 모든 코드가 특정 디렉토리(`GOPATH/src`) 아래에 있어야 했으나, 모듈 시스템 도입 이후에는 프로젝트 디렉토리가 어디에 있든 독립적인 모듈 단위로 관리가 가능해졌습니다. 이는 프로젝트별로 서로 다른 라이브 ․ 라이브러리 버전을 사용하는 것을 가능하게 하여, 개발 환경의 유연성을 극대화했습니다.

### 2. `go.mod` vs `go.sum` 쌍의 역할
- **`go.mod`**: 프로젝트의 모듈 이름, Go 언어 버전, 그리고 프로젝트가 의존하는 외부 패키지들의 명세(Dependency Graph)를 정의하는 핵심 파일입니다.
- **`go.sum`**: 다운로드된 각 외부 패키지의 체크섬(Checksum) 값을 저장합니다. 패키지 내용이 변조되었는지 확인하여, 중간자 공격(MITM)이나 외부 저장소의 비정상적인 변경으로부터 소스 코드의 무결성을 보장하는 보안 장치 역할을 합니다.

### 3. `go mod tidy`의 마법
`go mod tidy` 명령어는 소스 코드 내의 `import` 문을 정밀하게 스캔합니다. 코드에서 사용 중인 패키지는 `go.mod`에 추가하고, 더 이상 사용되지 않는(Unused) 오래된 의존성은 자동으로 제거하여 프로젝트의 의존성 그래프를 항상 최적의 상태로 유지합니다.

### 4. `go mod vendor`와 의존성 격리 (Hermeticity)
- **개념**: `go mod vendor` 명령은 외부 패키지 소스 코드를 프로젝트 루트의 `vendor/` 디렉토리로 직접 복사해 옵니다.
- **장점**:
    - **네트워크 독립성 (Offline Build)**: 외부 네트워크 연결이 불가능한 환경이나 CI/CD 서버에서도 `vendor/` 내의 소스만으로 즉시 빌드가 가능합니다.
    - **재현성 (Reproducibility)**: 외부 패키지 저장소(GitHub 등)에 문제가 생기거나 패키지가 삭제되더라도, 프로젝트 내부에 복사본이 있으므로 빌드 안정성을 보장합니다.
- **검증 방식**: `go run -mod=vendor .` 플래그를 사용하면 Go 컴파일러가 외부 저장소를 확인하지 않고 오직 `vendor/` 폴더 내의 소스만을 참조하도록 강제하여, 완벽한 의존성 격리를 테스트할 수 있습니다.
